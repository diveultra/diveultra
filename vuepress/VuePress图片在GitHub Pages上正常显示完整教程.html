# 1. 问题背景：为什么图片显示不出来？

# 1.1 常见错误现象

在 VuePress 博客部署到 GitHub Pages 后，经常遇到以下问题：

  • ❌ 本地 Typora 能正常显示图片，但博客网站显示不出来
  • ❌ 图片路径是相对路径，GitHub Pages 访问时路径解析错误
  • ❌ 图片放在 .assets 隐藏文件夹，构建时可能被忽略
  • ❌ 使用绝对路径（如 /Users/xxx/...），部署后完全失效

# 1.2 根本原因分析

# 原因一：路径解析差异

本地开发环境：

  • Markdown 编辑器（如 Typora）直接读取本地文件系统
  • 相对路径 ./xxx.assets/image.png 基于当前 Markdown 文件的磁盘位置解析
  • 可以正常显示

GitHub Pages 部署环境：

  • 所有文件都通过 HTTP 访问
  • 相对路径基于网站根目录解析，而不是 Markdown 文件位置
  • 如果图片路径是 ./xxx.assets/image.png，浏览器会尝试访问 https://your-site.github.io/xxx.assets/image.png
  • 但实际构建后的文件结构可能不同，导致 404

# 原因二：VuePress 构建机制

VuePress 在构建时会：

  1. 将 docs/ 目录下的 Markdown 文件编译为 HTML
  2. 将 docs/.vuepress/public/ 目录下的文件原样复制到构建输出的根目录
  3. 其他资源文件需要正确引用才能被打包

关键点： public/ 目录下的文件会直接映射到网站根目录！

# 2. VuePress 图片处理机制解析

# 2.1 VuePress 目录结构

vuepress-diveultra/
├── docs/
│   ├── .vuepress/
│   │   ├── public/          # 静态资源目录（重要！）
│   │   │   └── images/      # 图片统一存放位置
│   │   ├── config.js        # 配置文件
│   │   └── scripts/        # 自定义脚本
│   ├── PHP/
│   │   ├── xxx.md
│   │   └── xxx.assets/      # Typora 自动生成的图片目录
│   └── ...
└── package.json

# 2.2 public 目录的作用

docs/.vuepress/public/ 目录中的文件：

  • ✅ 构建时会原样复制到 dist/ 根目录
  • ✅ 可以通过绝对路径 /images/xxx.png 访问
  • ✅ 不受 Markdown 文件位置影响

示例：

  • 源文件：docs/.vuepress/public/images/logo.png
  • 构建后：dist/images/logo.png
  • 访问路径：https://your-site.github.io/images/logo.png

# 2.3 图片路径引用方式对比

引用方式 本地 Typora GitHub Pages 推荐度
./xxx.assets/image.png ✅ 正常 ❌ 可能失败 ⭐⭐
../assets/image.png ✅ 正常 ❌ 可能失败 ⭐⭐
/images/image.png ❌ 无法显示 ✅ 正常 ⭐⭐⭐⭐⭐
/Users/xxx/... ✅ 正常 ❌ 完全失效 ❌

结论： 使用 /images/xxx.png 格式，既能在 GitHub Pages 正常显示，又能通过自动化脚本在本地和部署环境之间切换。

# 3. 解决方案：使用 public 目录统一管理图片

# 3.1 方案概述

核心思路：

  1. 将所有需要发布的图片统一放到 docs/.vuepress/public/images/ 目录
  2. 在 Markdown 文件中使用绝对路径 /images/xxx.png 引用
  3. 构建时图片会自动复制到 dist/images/，部署后可以正常访问

# 3.2 手动操作步骤

# 步骤 1：创建图片目录

mkdir -p docs/.vuepress/public/images

# 步骤 2：复制图片到 public/images

将你的图片文件（从 .assets 目录或其他位置）复制到 public/images/：

# 示例：复制 PHP 目录下的图片
cp docs/PHP/macOS\ 下利用\ Homebrew\ 管理\ PHP\ 版本全流程.assets/*.png \
   docs/.vuepress/public/images/

# 步骤 3：修改 Markdown 文件中的图片路径

修改前：

![描述](./macOS 下利用 Homebrew 管理 PHP 版本全流程.assets/image-xxx.png)

修改后：

![描述](/images/image-xxx.png)

# 步骤 4：构建和部署

npm run build
npm run deploy

# 3.3 方案优缺点

优点：

  • ✅ 图片路径统一，易于管理
  • ✅ GitHub Pages 100% 可以正常显示
  • ✅ 不受 Markdown 文件位置影响

缺点：

  • ❌ 本地 Typora 无法直接预览（因为 /images/ 是网站路径）
  • ❌ 需要手动维护两套路径（本地用相对路径，部署用绝对路径）

# 4. 自动化脚本：一键处理图片路径

为了解决手动操作的痛点，我们创建了自动化脚本，实现本地编辑和博客部署两不误。

# 4.1 脚本功能

脚本位置：docs/.vuepress/scripts/prepare-blog-images.js

核心功能：

  1. 发布前准备（prepare）：

    • 自动将 Markdown 中的相对路径替换为 /images/xxx.png
    • 自动复制 .assets 目录下的图片到 public/images/
    • 保存原始路径到备份文件，用于后续恢复

  2. 发布后恢复（restore）：

    • 根据备份文件恢复所有图片路径为原始相对路径
    • 删除备份文件
    • 恢复后本地 Typora 可以正常显示

# 4.2 脚本支持的路径格式

脚本可以自动处理以下格式的图片路径：

  1. 相对路径（.assets 目录）：

    ![alt](./xxx.assets/image.png)
![alt](xxx.assets/image.png)

  2. 绝对路径（包含 public/images）：

    ![alt](/Users/xxx/docs/.vuepress/public/images/image.png)

  3. 已经是 /images/ 格式的会跳过：

    ![alt](/images/image.png)  # 不处理

# 4.3 使用方法

# 安装脚本（已集成到 package.json）

{
  "scripts": {
    "blog:prepare": "node ./docs/.vuepress/scripts/prepare-blog-images.js prepare",
    "blog:restore": "node ./docs/.vuepress/scripts/prepare-blog-images.js restore"
  }
}

# 发布前准备

处理整个 docs 目录：

npm run blog:prepare

处理指定目录：

npm run blog:prepare -- docs/english
npm run blog:prepare -- docs/PHP
npm run blog:prepare -- english  # 自动加上 docs/ 前缀

执行效果：

  • ✅ 所有图片路径替换为 /images/xxx.png
  • ✅ 图片复制到 public/images/
  • ✅ 备份文件保存到 .vuepress/.image-path-backup.json

# 发布后恢复

npm run blog:restore

执行效果：

  • ✅ 所有图片路径恢复为原始相对路径
  • ✅ 本地 Typora 可以正常显示
  • ✅ 备份文件被删除

# 6. 常见问题排查

# 6.1 问题：执行 prepare 后，本地 Typora 看不到图片

原因： 图片路径已改为 /images/xxx.png，这是网站路径，本地文件系统无法解析。

解决：

  1. 发布前才执行 prepare，平时写作不要执行
  2. 发布后执行 restore 恢复本地路径
  3. 或者使用 Git 分支管理：main 分支保持相对路径，gh-pages 分支使用绝对路径

# 6.2 问题：GitHub Pages 上图片显示 404

排查步骤：

  1. 检查图片是否在 public/images/ 目录：

    ls docs/.vuepress/public/images/

  2. 检查构建后的 dist 目录：

    ls docs/.vuepress/dist/images/

    如果图片不在 dist 目录，说明构建时没有正确复制。

  3. 检查 Markdown 中的路径格式：

    grep -r "\.assets" docs/english/*.md

    如果还有 .assets 路径，说明 prepare 没有执行或执行失败。

  4. 检查 GitHub Pages 设置：

    • 确保发布源是 gh-pages 分支
    • 确保发布目录是 / (root)

  5. 检查图片文件名：

    • 避免中文和特殊字符
    • 建议使用英文、数字、连字符、下划线

# 6.3 问题：执行 restore 后找不到备份文件

原因： 备份文件可能被误删，或者没有执行过 prepare。

解决：

  1. 检查备份文件是否存在：

    ls docs/.vuepress/.image-path-backup.json

  2. 如果文件不存在，需要重新执行 prepare 才能 restore

  3. 如果备份文件损坏，可以手动恢复：

    • 查看 Git 历史记录
    • 或者重新执行 prepare（会覆盖当前路径）

# 6.4 问题：图片文件名冲突

原因： 不同目录下的 .assets 文件夹可能有同名图片。

解决：

  1. 脚本会自动处理：后复制的图片会覆盖先复制的（同名文件）
  2. 建议：在 prepare 前检查是否有同名图片：
    find docs -name "*.png" -path "*.assets/*" | xargs -I {} basename {} | sort | uniq -d
  3. 如果发现冲突，可以手动重命名图片

# 6.5 问题：脚本执行报错 "目录不存在"

原因： 路径参数错误。

解决：

  • 使用相对路径：docs/english 或 english
  • 不要使用绝对路径
  • 确保在项目根目录执行命令

# 7. 最佳实践建议

# 7.1 图片命名规范

推荐格式：

image-20251226102056328.png
screenshot-2025-01-01.png
diagram-flowchart.png

避免：

图片1.png          # 中文
my image.png       # 空格
image@2025.png     # 特殊字符

# 7.2 目录组织建议

方案一：按文章分类（推荐）

docs/
├── PHP/
│   ├── article1.md
│   └── article1.assets/
├── JAVA/
│   ├── article2.md
│   └── article2.assets/
└── .vuepress/
    └── public/
        └── images/  # 所有图片统一存放

方案二：按日期分类

docs/.vuepress/public/images/
├── 2025/
│   ├── 01/
│   │   └── image-xxx.png
│   └── 02/
└── 2024/

# 7.3 Git 管理建议

推荐 .gitignore 配置：

# 备份文件（自动生成，不需要提交）
docs/.vuepress/.image-path-backup.json

# 构建输出（不需要提交）
docs/.vuepress/dist/
node_modules/

提交策略：

  • ✅ 提交原始 Markdown 文件（相对路径）
  • ✅ 提交 public/images/ 目录下的图片
  • ❌ 不提交备份文件
  • ❌ 不提交构建输出

# 7.4 工作流程优化

使用 Git 分支管理（高级）：

# main 分支：保持相对路径，用于本地编辑
git checkout main

# 发布时：切换到 deploy 分支
git checkout -b deploy
npm run blog:prepare
npm run build
# 提交构建结果到 gh-pages 分支
git subtree push --prefix docs/.vuepress/dist origin gh-pages

# 切回 main 分支继续编辑
git checkout main

# 7.5 性能优化建议

  1. 图片压缩： 使用工具压缩图片（如 TinyPNG）减少文件大小
  2. 图片格式： 优先使用 WebP 格式（需要浏览器支持）
  3. 懒加载： 使用 VuePress 插件实现图片懒加载
  4. CDN： 将图片放到 CDN（如 GitHub Issues、云存储）

# 8. 总结

# 核心要点

  1. 问题根源： 本地文件系统和 HTTP 服务器的路径解析机制不同
  2. 解决方案： 使用 public/images/ 目录 + 绝对路径 /images/xxx.png
  3. 自动化工具： 使用脚本在本地路径和部署路径之间自动切换
  4. 最佳实践： 本地写作用相对路径，部署时自动转换为绝对路径
